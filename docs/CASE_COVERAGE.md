# Покрытие кейса «Умный кредитный кабинет предпринимателя»

Сверка с официальным PDF «Альфа_Хак_Умный_кредитный_кабинет», с. 2–15, по состоянию на 24 октября 2026 года. Здесь оценивается **текущий путь React + Go**, а не прежний Python-прототип в общем репозитории. `IMPLEMENTED` означает работающий код этого пути; наличие маршрута в OpenAPI само по себе не означает реализацию. Контракт и статусы операций описаны в backend `api/FRONTEND_INTEGRATION.md` и `api/openapi.yaml`.

## Клиент без счёта в Альфа-Банке

В тестовых данных одна компания имеет `alfa_account`, две — `external_account`. Для внешнего клиента доступны вход, подбор, черновик и отправка заявки **без открытия счёта в Альфе**. Кабинет просит вручную указать обороты, объясняет, что банк пока не видит их по счёту в другом банке, и для оборотного кредита заранее показывает необходимость выписки. Go проверяет обязательность документа перед отправкой; файл сохраняется с заявкой. Для клиента Альфы известные учебные обороты подставляются, а выписка не требуется по умолчанию. Различие основано на сохранённом признаке компании и источнике финансовых данных, а не на выборе карточки на первом экране. См. также [карту путей](ACCOUNT_JOURNEYS.md) (кейс, с. 5, 9, 13).

Это **учебные профили**, а не полноценный вход нового предпринимателя. Регистрация произвольной компании, проверка содержимого выписки, подтверждение оборотов реальным банком, открытие счёта в Альфе и выдача средств не реализованы. Текущий интерфейс не должен объявлять деньги полученными после одного подбора, загрузки документа или scoring. Официальный кейс допускает моделирование подписания и выдачи без реальных операций (с. 11), но переходы и результат модели должны быть связаны с той же заявкой.

## Приоритеты перед сдачей

### P0 — целостность и проверяемость

- [ ] Довести **текущий** React + Go путь до опубликованного результата: подключить совместимый scoring, отдельно применить кредитные правила к его оценке и параметрам заявки, сохранить причины и итог `approved` / `counter_offer` / `rejected` либо обоснованный запрос данных. Скоринг и кредитное решение — разные этапы (с. 6, 9, 14–15). Если выбран `manual_review`, нужен проверяемый путь банковского решения.
- [ ] После результата дать клиенту действие в том же кабинете и по тому же `applicationId`: увидеть условия или причину отказа, принять либо отклонить предложение. Подписание и выдачу можно моделировать, но не показывать как свершившиеся без серверного перехода (с. 6, 9, 11, 15).
- [ ] Собрать frontend, Go backend, scoring и БД в один воспроизводимый Docker-запуск и проверить путь от новой заявки до результата на обычном ПК. Сейчас Go Compose запускает backend и PostgreSQL, а обновлённый React запускается отдельно; общий репозиторий закрепляет прежний Python-путь (с. 7, 9).
- [ ] Передать одну однозначную версию: обновить указатели подмодулей общего GitHub-репозитория на совместимые коммиты, указать commit hash или тег дедлайна и подтвердить доступ `alfa-hack-2026` ко всем приватным репозиториям (с. 7). Доступ жюри и дедлайн-версия не подтверждаются локальным исходным кодом.
- [ ] Собрать в репозитории сдачи комплект проверки: README с одним сценарием и окружением, `THIRD_PARTY_NOTICES`, архитектурную схему, описание API и OpenAPI, коллекцию запросов, диаграмму состояний, модель данных и тестовые сценарии. OpenAPI/Postman/fixtures уже есть в Go backend, notices — во frontend; явные схемы архитектуры, состояний и данных пока не найдены (с. 7).

### P1 — качество опыта и банковская сторона

- [x] Сделать проход жюри полностью внутри продукта без шага «получить SMS». Быстрый вход в один из двух сценариев выведен первым; телефон и тестовый OTP остаются дополнительным способом входа. Реальная SMS не отправляется (с. 11).
- [ ] Показать банковскую сторону через проверяемые состояния, причину запросов данных и аудит действий. Если MVP включает ручное рассмотрение, нужен доступный сценарий для роли сотрудника; если нет — зафиксировать границы автоматического процесса и правила решения (с. 4–6, 9, 13–15).
- [ ] Для клиента без счёта сделать явным момент, когда после одобрения требуется открыть счёт для выдачи, и не смешивать предварительно введённые обороты с подтверждёнными данными. Сейчас открытие счёта и проверка выписки не реализованы (с. 5, 9, 13–15).
- [ ] Связать найденные потребности клиента и банка с конкретными решениями и ограничениями MVP в документации; публичный конкурентный обзор уже есть, но пользовательское исследование не подтверждено (с. 6, 8–9, 12).

Кейс **не требует** обучать ML-модель, подключаться к БКИ/ФНС или переводить реальные деньги: источники на с. 13 приведены как примеры, правила скоринга допустимы на с. 14, а реальные подписание и выдачу разрешено моделировать на с. 11. Дополнительные функции ценны только после работающего основного сценария (с. 9).
